# Runbook

How to deploy and operate the live app, and what to do when something goes wrong.

|              |                                                                                      |
| ------------ | ------------------------------------------------------------------------------------ |
| **Live app** | https://neobank-sisir.onrender.com                                                   |
| **API docs** | https://neobank-sisir.onrender.com/api/docs/                                         |
| **Health**   | https://neobank-sisir.onrender.com/api/health (`version` is the deployed git commit) |
| **Hosting**  | Render free web service, Singapore, from `render.yaml`                               |
| **Database** | MongoDB Atlas M0 (free), AWS Singapore, database `neobank`                           |
| **Check it** | `npm run smoke -- https://neobank-sisir.onrender.com`                                |

## Environment variables

| Variable             | Where it comes from          | Notes                                                                                               |
| -------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------- |
| `NODE_ENV`           | `render.yaml`: `production`  | Turns on `Secure` cookies and the production checks below                                           |
| `MONGODB_URI`        | You, in the Render dashboard | Atlas string ending in `/neobank?…`. Required in production                                         |
| `JWT_ACCESS_SECRET`  | Generated by Render          | Signs access tokens. 32+ characters, required in production                                         |
| `MFA_ENCRYPTION_KEY` | Generated by Render          | Encrypts 2FA secrets. 32+ characters, required. **Never change it once anyone has 2FA** (see below) |
| `ADMIN_PASSWORD`     | You, in the Render dashboard | Creates `admin@neobank.dev` on start-up **if it doesn't exist yet**. Empty means no admin           |
| `SEED_DEMO_DATA`     | `render.yaml`: `'true'`      | Creates Priya and Ravi with history if they don't exist                                             |
| `AUTH_RATE_LIMIT`    | Default 20                   | Login/register attempts per IP per 15 minutes; refresh gets 10×                                     |
| `RENDER_GIT_COMMIT`  | Set by Render                | Shown as `version` by `/api/health`                                                                 |

If a required variable is missing or invalid, the API logs `Invalid environment variables:` with the reason and exits, and Render keeps the previous deploy running.

## First deployment

**1. MongoDB Atlas** ([cloud.mongodb.com](https://cloud.mongodb.com))

1. Create a cluster: **M0 (free)**, provider **AWS**, region **Singapore (ap-southeast-1)**, the same region as the Render service. (Mumbai has no free tier, and the database should sit next to the server rather than the users: one page makes several database calls.)
2. **Security → Database & Network Access → Database Users:** add a user with an auto-generated password and copy it. Atlas never shows it again; use **Edit → Edit Password** to set a new one.
3. **IP Access List → Add IP Address → Allow Access from Anywhere** (`0.0.0.0/0`). Render's free tier has no fixed outgoing IP. The database stays protected by the user's password and TLS.
4. **Clusters → Connect → Drivers:** copy the connection string, replace `<db_password>` and add the database name before the `?`. Percent-encode `@ : / ? # %` in the password:
   `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/neobank?appName=Cluster0`

**2. Render** ([render.com](https://render.com))

1. In `render.yaml`, set `name` to something unique on Render. It becomes `https://<name>.onrender.com`. Commit and push.
2. Sign in with GitHub, then **New → Blueprint** → pick this repository.
3. Enter `MONGODB_URI` (from step 1.4) and `ADMIN_PASSWORD`. Render generates the two secrets.
4. **Apply.** The first Docker build takes 5–10 minutes. The logs should end with `[db] connected to …/neobank` and `[api] ready`.

**3. Check it:** run the smoke test, then log in as the admin and set up 2FA with your phone. Save the backup codes somewhere safe.

## Everyday operations

### Deploying

Every push to `main` deploys automatically, while CI runs in parallel. To deploy only after CI passes, set Render's **Auto-Deploy** to _After CI checks pass_. After a deploy, check `/api/health` shows the new commit, then run the smoke test.

### Rolling back

Render dashboard → the service → **Events** → find the last good deploy → **Rollback**. Then fix forward with a new commit: the next push deploys again. Database changes are not rolled back; so far nothing in the app changes stored data on deploy.

### Logs

Render dashboard → the service → **Logs**. Useful lines: `[db] connected`, `[api] ready`, `[api] SIGTERM received` (a normal restart or sleep), `[api] failed to start` (look at the next lines).

### Resetting demo data

Log in as the admin → **Admin → Reset demo data**. This deletes Priya and Ravi with everything they own (accounts, history, beneficiaries, sessions) and recreates them with fresh history. Other users are untouched. A restart does **not** reset them: seeding skips users that already exist.

## When something goes wrong

### The "Keep alive" workflow failed (you got an email)

Open the failed run in **Actions**; the log names the failed check.

| Failed check                                                     | Likely cause                                           | What to do                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `Service did not become healthy: 503 db=down`                    | The API is up but can't reach MongoDB                  | See _Database unreachable_ below                                              |
| `Service did not become healthy: fetch failed` (or a JSON error) | The service is suspended, deleted or renamed           | Check the Render dashboard. If renamed, set the repository variable `APP_URL` |
| `Demo user can log in` (401)                                     | Someone changed the demo password or turned on its 2FA | See _The public demo login stopped working_                                   |
| Header or caching checks                                         | A code change                                          | Compare with the last green run; the CI Docker job should have caught it      |

After fixing, re-run it from **Actions → Keep alive → Run workflow**.

### Database unreachable (`/api/health` returns 503, `"db":"down"`)

1. **Atlas paused the cluster** after a long time without connections: Atlas → Clusters → **Resume**. Data is kept.
2. **IP access list changed:** make sure `0.0.0.0/0` is still there.
3. **Password changed** in Atlas: update `MONGODB_URI` in Render (Environment), which redeploys.
4. **Atlas incident:** check [status.mongodb.com](https://status.mongodb.com).

### The public demo login stopped working

The demo accounts are shared, and nothing stops a visitor from changing Priya's password or turning on her 2FA. Fix: **Admin → Reset demo data** recreates both demo users with the published password and no 2FA. (Blocking these changes for demo users is planned for Day 8.)

### The admin is locked out

- **5 wrong passwords or codes:** wait 15 minutes; the lock clears itself.
- **Lost phone:** sign in with one of the backup codes, then **Security → Set up** again on the new phone.
- **Lost phone and backup codes:** in Atlas → **Data Explorer** → `neobank.users`, find the admin and set `mfa.enabled` to `false` (and remove `mfa.secretEnc`). The next sign-in forces a fresh 2FA setup.
- **Forgot the password:** changing `ADMIN_PASSWORD` on Render does nothing once the admin exists. Delete the admin's document in `neobank.users`, then restart the service (**Manual Deploy → Restart service**); start-up recreates it with the current `ADMIN_PASSWORD`. The audit log keeps its old entries.

### Rotating secrets

| Secret               | Effect of changing it                                                                                                     | Safe?                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `JWT_ACCESS_SECRET`  | Current access tokens stop working. Browsers refresh automatically (refresh tokens aren't JWTs), so nobody is signed out. | Yes, any time it may have leaked         |
| Atlas user password  | The app can't connect until `MONGODB_URI` is updated. Change both together.                                               | Yes, with a minute of downtime           |
| `MFA_ENCRYPTION_KEY` | Every stored 2FA secret becomes unreadable: nobody with 2FA can sign in, including the admin.                             | **No.** Only with a re-encryption script |
| `ADMIN_PASSWORD`     | Nothing, once the admin exists (see above). Change the password on the Security page instead.                             | n/a                                      |

To regenerate a Render-generated value: Render → Environment → the variable → **Generate**, then save (it redeploys).

## Free-tier limits

- **Render sleeps** after 15 minutes without traffic; the first request then takes 30–60 seconds. The smoke test waits for it. 750 free hours a month covers one service.
- **Atlas M0:** 512 MB storage and **no backups**. Demo data can always be rebuilt, but real sign-ups can't. A cluster with no connections for a long time can be paused; the weekly _Keep alive_ workflow prevents that.
- **GitHub:** scheduled workflows are disabled after 60 days without commits. GitHub emails first; re-enable from the Actions tab.
